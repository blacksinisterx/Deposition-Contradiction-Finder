# Deposition Contradiction Finder — Written Note

**Live app:** https://deposition-contradiction-finder.vercel.app/
**Repo:** https://github.com/blacksinisterx/Deposition-Contradiction-Finder

## What I built

An AI litigation-prep agent that takes multiple witness depositions from the same case, builds a per-witness timeline, and cross-references statements across documents to flag contradictions — each backed by an exact page/line citation from the original transcript, not a vague summary of "these seem inconsistent."

The design goal, same as my first submission (Exploit-Path-Tracer): prove this is an agent doing multi-step reasoning over structured state, not a chatbot with a nicer UI. The proof mechanic here is a direct analogue of that project's false-positive dismissal: plant a pair of statements that share a keyword and *look* contradictory to naive matching, but refer to two entirely different facts on a careful read. A keyword or embedding-similarity matcher gets this wrong immediately. The agent has to get it right in both directions — confirm the pairs that are genuinely contradictory, and correctly dismiss the one that only sounds like it is.

## Architecture, and why each piece is shaped the way it is

**The transcript parser is a real, deterministic tool — the citations are never something the LLM has to get right from memory.** Depositions follow the standard court-reporter convention: `[page:line] Q./A. text`. A regex parser extracts exact `{page, line, speaker, text}` for every exchange before any LLM sees the document. When `extract_claims` pulls a factual claim out of the transcript, it never states its own page/line — it only refers to the claim by an index into the numbered exchange list the parser already produced. The real citation gets stitched back on afterward, deterministically, from the parser's own output. This is the same "ground-truth tool feeds the LLM, LLM never invents the anchor" division of labor that Semgrep played in my first project, applied to a completely different domain.

**Grouping needed a real architectural fix, not a heuristic patch, to handle self-reference vs. other-reference.** A witness describing their own status almost never names themselves — "I was standing right next to the forklift" — while a different witness describing that same person's status always does — "Kessler wasn't even on the floor." No amount of tuning a shared-keyword threshold closes that gap, because the two claims share zero name overlap by construction. I added an explicit `about_person` field to `extract_claims`'s output schema (the surname of who the claim's status is about — self or a named other), and grouping matches on shared `about_person` in addition to shared topic vocabulary. This required a real schema migration (`ALTER TABLE claims ADD COLUMN about_person`) mid-build, not just a prompt tweak, because it changes what gets persisted, not just how two already-persisted claims get compared.

**Model selection was a real, multi-round investigation, and the smaller model's failure is itself a finding worth keeping.** The original plan (mirroring my first project) was Groq's `llama-3.3-70b-versatile`, but it hit its daily token quota mid-build, during debugging of an unrelated grouping bug (see below), before it could be evaluated on the actual task. Its replacement, `llama-3.1-8b-instant`, ran without errors on a full pass — but 18 of its "confirmed" contradictions were spurious. One example: it called a witness's "I'm a warehouse loader" a contradiction of another witness's "he was on his break," reasoning that stating a job title "implies presence." That is *exactly* the naive pattern-matching failure this entire product exists to catch — a model making that mistake itself isn't just noisier, it's disqualifying for the task. I checked Groq's live model list (not memory — the plan's originally-documented fallback, `deepseek-r1-distill-llama-70b`, had been decommissioned since I wrote it down) and landed on `openai/gpt-oss-120b`, verifying it directly against four hand-picked pairs — the two genuine contradictions, the warning-light near-miss, and the specific job-title-vs-whereabouts pair the smaller model got wrong — before trusting it with a full run. All four came back correct, with reasoning that correctly distinguished "general employment fact" from "a claim about a specific moment."

**Agent compute is GitHub Actions `workflow_dispatch`, applied from day one instead of rediscovered.** My first project burned three real hosting dead ends (Hugging Face Docker SDK paywalled, Gradio SDK's ZeroGPU hardware structurally incompatible with a plain FastAPI process, Render demanding a card despite advertising a free tier) before landing on on-demand GitHub Actions jobs. This time I went straight there — it required, again, zero changes to the actual LangGraph harness, just a thin CI entrypoint (`ci_run_analysis.py`) that downloads the uploaded transcripts and runs the unchanged graph. `workflow_dispatch` inputs are scalar strings only, so passing a variable-length document list required JSON-encoding it into one input (`documents_json`) and parsing it in the entrypoint — a small, genuinely new wrinkle this project's multi-document shape introduced that the single-zip-upload shape of the first project never needed to solve.

## Other real bugs found during the build (a sample — the full log is in `PLAN.md`)

- **Grouping was badly over-loose on the first real run.** Flattening every claim's tags into one word-bag and matching on any single shared word let a witness's own name (recurring across dozens of unrelated claims) count as a topic match — 31 claims produced 119 candidate pairs instead of the ~3 designed ones, and burned through Groq's entire daily quota partway through `cross_reference`. Fixed by matching at the individual-tag level with a subset-containment check, excluding single-word tags as too generic to anchor a match.
- **A second, subtler grouping miss survived that fix.** Even after tightening, one clean run still missed the exact designed warning-light pair — inspecting the actual stored tags showed the LLM had split "hydraulic warning light" into two separate tags on Kessler's side that run, while Torres's side used one combined tag. Strict per-tag matching structurally can't catch a concept split differently across two independently-generated tag sets. Fixed by matching on ≥2 shared significant words across each claim's *flattened* tag vocabulary instead — verified offline against the actual stored claim data (zero LLM cost) that this closes the gap without reopening the original over-grouping bug; the threshold of 2, not 1, is specifically what keeps a lone shared witness name from matching everything again.
- **A `max_tokens` truncation that looked like a reasoning failure.** One document kept producing zero claims from a model that was otherwise working fine. Bypassing the retry-then-fallback wrapper to see the raw exception showed a valid, well-formed claims list cut off mid-token — `ChatGroq` had never been given an explicit `max_tokens`, so it hit an unstated default cap on a longer document. Fixed by setting `max_tokens=4096` explicitly.
- **Groq's rate-limit ETA is misleading for a daily cap.** The error message's stated "~15 min" grew to 21+ minutes on a recheck a few minutes later, with usage barely moved — it's a genuinely long daily token cap (100,000 TPD on the free tier), not a short cooldown. The real fix was discovering (and verifying directly against the API) that Groq buckets rate limits *per model*, so switching models gives immediate access to a fresh quota rather than waiting out an unknown-length cooldown.

## Honest limitations

- `parse_documents` only handles the plain-text `[page:line] Q./A.` court-reporter format used in the fixture. Real PDF/OCR ingestion of arbitrary deposition transcripts was explicitly cut to a stretch goal, not attempted.
- Grouping is a real, tuned heuristic (shared tag vocabulary + shared subject), not a guarantee of finding every true cross-document link — a contradiction phrased with zero topical or subject overlap to its counterpart would not be surfaced as a candidate pair at all. Fine at fixture scale; a production version would want a broader recall pass (e.g. embedding similarity as a second candidate source) with the same LLM judgment step as the precision filter.
- Groq's free tier has real per-model daily token caps. Fine for a demo-scoped build with a handful of depositions; not something to point at a large multi-witness case archive without checking current limits.
- No human-in-the-loop review step before a contradiction is marked `confirmed` — in a real litigation-prep tool, every agent verdict would need attorney sign-off before it's relied on for anything, which this demo doesn't model.

## What I'd build next

Embedding-based candidate generation as a second, higher-recall pass alongside the current tag/subject grouping — the current heuristic is precise but has a real recall ceiling for contradictions that don't share obvious topic or subject overlap. After that: real PDF/OCR transcript ingestion, and a review/approval workflow so a human attorney explicitly confirms or overturns each agent verdict before it's treated as final.
